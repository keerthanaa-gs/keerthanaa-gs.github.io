Frontend architecture

Rich text editing system

A reusable formatted-content component for enterprise workflows — from editor state to API persistence and back.

how I thought & built it

How I thought

A normal input captures text; the product needed users to create formatted content that survives — saved, reloaded, re-edited without breaking. The hard half isn't creating content, it's rehydrating stored content faithfully when a user returns. And it had to be one reusable component, not a fresh editor rebuilt on every page.

How I built it

User → Editor state → Structured content → Form state → API → Database → (reload) → Editor re-initialized

A controlled component managing editor state, translating formatting actions (headings, lists, links, emphasis) into structured content, integrating with form state, persisting through the API, and initializing correctly from stored values on edit. Exposed as one component with props — value, onChange, disabled — so behavior changes happen once, everywhere.

Backend infrastructure

Configurable email infrastructure

SMTP managed through configuration, not hardcoding — with a test-email workflow that verifies the full chain.

how I thought & built it

How I thought

Enterprise software runs in many customer environments, and every one has different mail infrastructure. Hardcoding SMTP means redeploying per customer — so settings had to live in a key-value configuration layer (host, port, credentials, sender, TLS) that admins control. And because SMTP fails in a dozen ways, admins needed to prove the configuration works before the system depends on it.

How I built it

Admin config UI → API → Config store → Email service reads config → SMTP connection → Send → Success / meaningful failure

The test-email feature sounds tiny but exercises everything: frontend validation, the API, the backend service, a live SMTP connection, and honest error feedback — loading, success, or a failure message an admin can actually act on.

Async processing

Background jobs with Hangfire

Bulk and automated email moved out of the HTTP request lifecycle entirely.

how I thought & built it

How I thought

Sending 1,000 emails inside one HTTP request is a design failure: the request times out, the user waits, a crash halfway is unrecoverable, and the server sits blocked. The principle — separate long-running work from the user's synchronous request. The API's job is to accept the work, not perform it.

How I built it

Trigger → API creates job → responds immediately ⋮ Worker → recipients + template → generate → SMTP → record result

Automated and bulk email ran as Hangfire background jobs — the queue absorbs load, workers process independently, failures become retryable instead of catastrophic, and the app stays responsive throughout.

Config-driven UI

Dynamic form engine

Forms rendered from configuration, not hardcoded — one renderer, many forms.

how I thought & built it

How I thought

Hardcoding every form doesn't scale in enterprise software — the product needed forms defined as data: a field definition says what it is, whether it's required, and how it validates; the UI figures out the rest. Validation had to be configuration-driven too, or the whole idea collapses.

How I built it

Form definition (JSON) → field type → component resolution → render → validation rules → form state → API

A renderer that reads field definitions, resolves each to the right component (text, dropdown, date...), applies declared validation constraints, and manages state through to submission. This is metadata-driven UI — and the direct ancestor of the JSON-configured low-code work I do at Fieldproxy today.

Offline architecture

Offline-first PWA

Local persistence with IndexedDB, synchronization when connectivity returns.

how I thought & built it

How I thought

Industrial and field users can't assume connectivity — so the normal browser→API→server model breaks exactly when they need the app most. The real questions: what must stay available offline, what does the user see without a network, and how do local changes reconcile with the server when connectivity returns?

How I built it

Online: App → API → Server ⋮ Offline: App → IndexedDB → (reconnect) → Sync → API

PWA capability via VitePWA with IndexedDB as proper structured local storage (far beyond localStorage), keeping relevant data usable offline and synchronizing local changes back to the server on reconnect.

Data-heavy UI

Enterprise data tables + React Query

Server-side pagination, filter-to-query mapping, and real server-state management.

how I thought & built it

How I thought

You never fetch 500,000 rows to show 20. And server state is not UI state — data living on the server needs caching, staleness handling, and refetch logic, which is a different problem from whether a modal is open. Scattering manual API calls solves neither.

How I built it

page + filters → query params → API → LIMIT/OFFSET → 20 rows → React Query cache → UI

Reusable, column-configurable tables with server-side pagination, filters mapped to API queries, and React Query managing the fetch lifecycle — caching, loading and error states, refetching — in one place instead of everywhere.

Identity & platform

Enterprise auth & configuration

Okta authentication plus the configuration layer that adapts one codebase to many environments.

how I thought & built it

How I thought

Enterprises don't want a homegrown login — they want their identity provider to own authentication. The app's job is to integrate cleanly: know who the user is, protect what needs protecting, attach identity to every API call. Same with time: the server thinks in UTC, every customer lives in their own timezone, and logs, reports, and schedules all inherit that decision.

How I built it

User → Okta → token → protected routes → authenticated API access

Okta-based auth handling tokens, sessions, protected routes, and authenticated API calls — alongside timezone and application configuration so stored UTC timestamps render correctly per environment across logs, notifications, and reports.

Case study

Enterprise integration · Financial services · Fieldproxy

Moving sensitive data without a human in the middle

The complaint

A financial services client needed sensitive data flowing into our platform regularly. The existing way was manual — files prepared and uploaded by hand — which for a regulated company meant every transfer was a security question waiting to be asked.

Mapping the real process

I walked their actual flow, not the assumed one: where data originates, who touches it, what happens when a file is malformed, what security needed to sign off. The real requirement wasn't "upload files" — it was "move sensitive data on a schedule without a human being the risk."

Worth solving?

Recurring, not one-time — every manual cycle cost effort and carried risk, and it blocked the account from scaling. The harder call was scope: what we commit to now versus later.

The handoff

A spec for automated encrypted ingestion (AES-256), covering the format contract, encryption approach, and how malformed data fails loudly instead of silently. Two explicit lists went to both engineering and the client: confirmed capabilities vs. feasibility-check items — so nobody built, or was promised, something unvalidated.

The lesson that stuck: clients don't buy features. They buy confidence that someone owns the outcome — and that confidence is built in the gap between "confirmed" and "we're still checking."

How I work

// opinions formed by shipping, not reading

01The spec is the easy part

Anyone can generate a spec with AI now. The job is what's around it: understanding users, making trade-offs, and owning whether the outcome actually happened.

02Confirmed ≠ probably

Every enterprise project I've run stays alive on one discipline: never letting "what we've confirmed" blur into "what we're still validating" — with clients or with engineering.

03Build with AI, verify like it's client data

I use Claude Code and Cursor daily. AI output gets the same distrust as a legacy data export: guards, validation, review. "Usually correct" is a failure mode in production.

04Adoption is the only compliment

Kind feedback is noise. The signal is whether people come back tomorrow without being asked — and complain when it's missing. I've shipped things that got adopted and things that got ignored; the difference taught me more than any course.
